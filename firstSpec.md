# Self-contained HTML documents with a desktop host — Spec v0.1

Oct 6, 2026 · @mfroehli

## Purpose and philosophy

The product is a desktop host that opens single-file HTML documents, runs them safely and saves them in place without file pickers.

Every kind of data gets its own dedicated UX, generated on the spot for its specific purpose. An hours sheet could be edited in Excel, but Excel is overkill; a purpose-built editor is much nicer to work with. So the document brings its UX with it. Documents are generated by Claude, following a simple document specification and supported by a skill (to be defined later). A user asks for an hours sheet, a checklist or a small database, receives a document that is its own dedicated editor, opens it in the host and works with it.

Behaviour is cheap to create and replace; data is durable. The user changes the data through the document's UX, and improves the UX itself through agentic coding when it falls short. The document carries both forward: the refined behaviour and the accumulated data live on in the same file.

Guiding principles:

- **The host is the product.** It must be robust, safe and pleasant for any document that follows the specification, including documents nobody has seen before.
- **The specification is the contract.** A short, precise document spec defines what a document contains and how it talks to the host. Generated documents are only as good as this spec and the skill built on it.
- **Thin, stable contract.** The host API stays small, versioned and backwards compatible. Data saved today must still open in a host years from now, even if the behaviour around it is regenerated.
- **Generated documents are untrusted code.** Nobody reviews a generated document line by line, so the host's sandbox is the safety net.
- **Data outlives behaviour.** The data block is what the user cares about; behaviour can always be regenerated around it.

The existing `hours-sheet.html` serves as the first test fixture and as the reference example for the document specification and the skill.

## User story

> As a user, I ask Claude for a simple hours sheet and receive a generated document. I double-click it, add today's work session and press Ctrl+S, so that the hours are saved into that same file without any file dialog or permission prompt.

Acceptance criteria:

- [ ] Double-clicking a document file (or dropping it on the host) opens it in the host and selects it in the document list. *(M1: drag and drop and command line; double-click with M3, document list with M2)*
- [ ] The document renders exactly as it does in Chrome. *(M1: awaiting manual check)*
- [ ] Ctrl/Cmd+S and File → Save write the current data into the opened file. No dialog appears. The document shows no Save button of its own while running in the host. *(M1: awaiting manual check)*
- [x] After saving, reopening the file shows the new rows.
- [x] Saving changes only the data block on disk. All other bytes of the file stay identical.
- [ ] Closing a document with unsaved changes asks: Save, Don't save, Cancel. *(M1: awaiting manual check)*
- [x] A failed write leaves the original file intact and shows an error.
- [x] Any document that conforms to the specification works in the host without host changes; the hours sheet is only the first fixture.

## Scope of v0.1

v0.1 proves the loop open → edit → save in place for any document that follows the specification, tested with the hours sheet as the first fixture.

v0.1 is delivered in three milestones. Each one is usable on its own; the code session plan follows M1 → M2 → M3.

**M1 · Loop**: open → edit → save in place, safely.

- Electron host for macOS and Windows, built on `BaseWindow` + `WebContentsView` from the start: open via dialog, command-line argument and drag-and-drop; one document per window until M2.
- Host API v1 (pull model): the document answers save requests with its data and signals changes; the host owns saving and the dirty state.
- Atomic writes plus a version store: before every write the host keeps the previous file in a central store in the app data folder (last N saves plus one per day). Nothing but the short-lived `.tmp` is ever written next to a document.
- External-change detection: watch the open file, react per section (reload on behaviour change, never silently overwrite a changed data block).
- Sandboxed, offline document execution.
- Conformance check on open: refuse every file that breaks the specification (frame, sections, kit, data block, line endings, API version). The error lists the violations with a "Copy report" button (for an agent to repair) and points to opening the file in Chrome, where the fallback still works.
- Kit: recognition of published kits by hash (the "Update kit" command follows in M2).
- Document specification v1 as a standalone file (`docs/document-spec.md`), written so that a skill can follow it later.
- Hours sheet adapted to the specification as the first fixture.

**M2 · Workspace**: several documents in one window.

- Multiple documents per window: a collapsible document list on the side, switchable between a compact list (name, dirty marker, badges for conflict or kit update) and thumbnails of the rendered documents (like a PDF viewer's page sidebar). Each document is its own `WebContentsView` inside a `BaseWindow`; the host tracks which path belongs to which view.
- Kit update: offer "Update kit" for outdated kits, replacing only the kit after the user confirms (previous file kept in the version store).
- Close summary for several dirty documents (Save all / Review each / Cancel).

**M3 · Distribution**: installed, associated, self-updating.

- Signed installers for macOS (signed and notarised) and Windows (signed), as required by auto-update.
- File association: the installer offers "Open HTML documents with EverythingApp" (opt-in). A file is a document if and only if its content contains the `ev-host-api` meta tag, whatever its extension; documents go through the conformance check, every other file is handed to the default browser. Naming documents `<name>.ev.html` is a recommended convention, not a rule.
- Auto-update via GitHub Releases and `electron-updater`: the host checks the update feed at startup and via Help → Check for updates, downloads new versions in the background and installs them on restart. The refusal for a newer API version offers the same check.
- Version store clean-up at startup: each entry has a `meta.json` (absolute path, file name, `ev-doc-type`, data block hash, last seen). Parent folder missing (e.g. unmounted volume) → skip; file missing → mark orphaned; orphaned for 90 days → delete. A total size cap (e.g. 500 MB) removes the oldest orphans first, then the oldest versions of live documents, never a document's newest version.

**M4 · Privileges** (v0.2, not part of v0.1): documents can request privileges beyond the sandbox, and the user can grant them. See the open question "Privileges requested by a document".

Non-goals for v0.1, besides the skill that generates documents (defined once the specification is stable):

- Template upgrade (regenerate behaviour, keep data).
- Documents that rewrite their own code through the host API. The host never writes a section other than the data block (it may replace the kit, which is frame); behaviour is improved outside the host by an agent editing the file on disk (an in-host "Improve this document…" command may follow later).
- Attachments, multiple data blocks, network access, multi-user sync.
- Linux packaging.
- Re-linking the history of a moved document (match an orphaned store entry by file name, `ev-doc-type` and data block hash). `meta.json` already records what is needed.
- "Save as…" and "Follow moved documents": when a document's file is moved or deleted, the host now only says so; later it can save the open data to a new file or follow the file to its new place.
- Kit 1.1, fallback save UI: the document marks its Save button and status line (e.g. `data-ev-fallback`); the kit detects the host and hides them there, and wires them up in the browser, where the fallback needs them. Replaces the rule that the document itself decides from `doc.hosted`.
- "Revert to version" in the host UI (v0.1: restore by copying from the version store manually).
- Stashing unsaved local data across a reload, showing a diff against a changed data block on disk and suggesting a merge (later; v0.1 only offers keep mine / take disk / cancel). The merge step also offers "Save mine as a copy".

## Document specification

Every document, hand-written or generated, must satisfy this specification; it is the contract between the host and whatever produces documents, and v1 lives as `docs/document-spec.md`.

A document is a fixed **frame** with exactly three named **sections**: style, data and script. The frame is defined by this specification and is the same for every document, apart from a few frame fields (title, language, document type). It includes the **kit**, the spec-defined script that loads the data, talks to the host and implements the fallback save. Everything a generator or agent writes goes into a section.

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="ev-host-api" content="1">
  <meta name="ev-doc-type" content="hours-sheet" data-version="1.0">
  <title>Hours sheet</title>
  <style id="ev-style">/* style section */</style>
</head>
<body>
  <div id="ev-app"></div>
  <script type="application/json" id="ev-data">{"rows":[]}</script>
  <script id="ev-kit">/* kit: part of the frame, verbatim per API version */</script>
  <script id="ev-script">/* script section */</script>
</body>
</html>
```

| Section | Element | Written by | Contains |
| --- | --- | --- | --- |
| Style | `<style id="ev-style">` | Generator / agent | All CSS |
| Data | `<script type="application/json" id="ev-data">` | Host (and fallback) | The data block |
| Script | `<script id="ev-script">` | Generator / agent | All JavaScript; renders the UI into `#ev-app` |

Rules:

- **Namespace.** Every identifier defined by this specification starts with `ev` (`ev-` for meta names and ids, `ev` for JavaScript globals: `window.evHost`, `EvKit`). The script section must not define its own identifiers with this prefix.
- **Frame.** Nothing outside the frame and its three sections. No additional elements, scripts, styles or comments.
- **Kit.** `<script id="ev-kit" data-kit-version="1.0.0">` is part of the frame. Every published kit version has a fixed text, and the host checks the kit against the hashes of all published kits for the document's `ev-host-api` version; unknown or modified kits are rejected. The script section uses it (`EvKit.init(...)`) and never reimplements loading, host wiring or saving.
- **Sections.** Exactly one of each section, identified by its id. Behaviour lives only in the style and script sections; data lives only in the data section.

- **Data block.** The data section's content is valid JSON with every `<` written as `\u003c`, so data can never close the script tag.
- **Runtime UI.** All UI is rendered by the script section into `#ev-app` at load time. `#ev-app` is empty in the saved file.
- **Host owns saving.** When `window.evHost` is present, the document shows no Save button and registers neither a Ctrl/Cmd+S handler nor `beforeunload`; it signals changes via `evHost.markDirty()`. The host owns the save command, the dirty marker and the close prompt. Only without a host does the document show its own Save button and wire up the fallback (keyboard shortcut, `beforeunload`).
- **Self-contained.** No external scripts, stylesheets, fonts or images. Assets are inlined or embedded as data URIs.
- **API version.** `<meta name="ev-host-api">` declares the host API version the document expects.
- **Document type.** `<meta name="ev-doc-type">` names the type and its behaviour version. Used later for template upgrades.
- **Data shape.** Top-level JSON object. The hours sheet uses `{"rows":[{"date","person","task","hours","note"}]}` with `date` as `YYYY-MM-DD` and `hours` as a number.

Recommendations for generators (the future skill builds on these):

- Render an empty data block gracefully, so a fresh document starts usable.
- Keep behaviour readable rather than minified, so a person can inspect what a generated document does.
- Keep the data shape flat and documented in a comment at the top of the script section.

## Host API v1

The host exposes `window.evHost` through Electron's `contextBridge`. It is a pull API: the host decides when to save and asks the document for its data; the document never starts a write and never sends a file path.

| Member | Signature | Semantics |
| --- | --- | --- |
| `version` | `number` | Host API version, `1` for this spec. |
| `onSaveRequest` | `(handler: () => string) => void` | Registers the function the host calls when the user saves (menu, Ctrl/Cmd+S, close prompt). It returns the current data as JSON. |
| `markDirty` | `() => void` | One-way signal: the data changed since the last save. Drives the title marker and the close prompt. |

Dirty state belongs to the host. Each `markDirty()` bumps a change counter; a save records the counter at the moment it takes the snapshot. After a successful write the host clears the dirty marker only if no `markDirty()` arrived after that snapshot, so an edit made while saving is never marked as saved.

Preload (host side):

```js
const { contextBridge, ipcRenderer } = require('electron');
let saveHandler = null;
let changes = 0;
ipcRenderer.on('doc:request-save', (_e, requestId) => {
  if (saveHandler) ipcRenderer.send('doc:save-data', { requestId, json: saveHandler(), changes });
});
contextBridge.exposeInMainWorld('evHost', {
  version: 1,
  onSaveRequest: (fn) => { saveHandler = fn; },
  markDirty: () => ipcRenderer.send('doc:dirty', ++changes),
});
```

Document side:

The kit does this wiring; the script section only hands it the data and reports changes. Inside the kit:

```js
if (window.evHost) {
  evHost.onSaveRequest(() => JSON.stringify(getData()));  // host drives saving; no Save button, key binding or beforeunload
} else {
  showSaveButton(fallbackSave);                          // see Browser fallback
  bindSaveKey(fallbackSave);
  guardUnload();
}
```

In the script section (illustrative; the kit's exact interface is defined in the Document specification):

```js
const doc = EvKit.init({ getData: () => data });
const data = doc.data;          // parsed data block
// … render into #ev-app …
doc.changed();                  // wherever data changes → evHost.markDirty() or fallback dirty state
```

## Host behaviour

The main process owns all file access; it maps each window to exactly one file path and never takes a path from the document.

1. **Open.** Sources: File → Open dialog, command-line argument, drag-and-drop onto the app or window, and file association (double-click). The host first reads the file's head: without the `ev-host-api` meta tag the file is not a document and is handed to the default browser (any extension). For documents, the host runs the conformance check; on any violation it refuses to open the document and shows the report. Otherwise it creates a `WebContentsView` and stores `webContents.id → absolute path`.
2. **Load.** The window loads the document from the custom protocol `ev-doc://<random-id>/` (see Security model), never via `file://`. The document gets its own `WebContentsView` and an entry in the document list. The window title shows the active document's file name, prefixed with `•` while dirty. Thumbnails are captured from the live view (`capturePage`) when the user switches away from a document and after each save, and are held in memory only.
3. **Save.** File → Save, Ctrl/Cmd+S or the close prompt sends `doc:request-save` to the active document's view. The document answers with `doc:save-data`; the host looks up the path for the sending view, reads the current file from disk, replaces only the data block content and writes it (step 5).
4. **Dirty state.** `doc:dirty` marks the window dirty. After a successful write, the host clears the marker only if the snapshot's change counter is still the latest one.
5. **Write safely.** Copy the current file into the version store (`<app data>/EverythingApp/versions/<hash of absolute path>/`), write the new content to `<name>.tmp` in the same folder, then rename it over the original. On any error the original stays untouched and the error is returned to the document.
6. **External change.** The host watches the open file and hashes each section on load and after every save. When the file changes on disk:
   - Behaviour changed, window clean → reload automatically.
   - Behaviour changed, window dirty → banner: "This document was updated. Save my data and reload / Reload and discard my changes / Later".
   - Data block changed → never overwrite silently; the next save shows a conflict prompt: Keep mine / Take the version on disk / Cancel. The write itself checks again that the data on disk is still what the host last saw; if it is not, the same prompt appears.
   - File moved or deleted → the host says so ("moved or deleted"): changes exist only in the window, put the file back at its path and save again. The last saved version stays in the version store.
   - Reload (View → Reload) with unsaved changes asks: Save and reload / Discard and reload / Cancel.
7. **Close.** Closing a document that is dirty shows Save / Don't save / Cancel; Save triggers step 3. The window closes only when nothing is left unsaved: a failed save, or an edit made while saving, keeps it open. Save, close and reload run one at a time; close and reload wait for a running save. A save requested while another runs waits and then saves again with fresh data; if the running save fails or is cancelled, the waiting one is dropped. Closing the window with several dirty documents shows a summary: Save all / Review each / Cancel. Ctrl/Cmd+S and File → Save always act on the active document.
8. **Unexpected errors.** Any failure not handled elsewhere (opening, checking the disk, closing, reloading) shows an error dialog with a "Copy report" button: file, action, message, stack trace, host and Electron version.
9. **Menu.** File: Open, Save, Close, Reveal in folder. View: Document list (show/hide), List / Thumbnails, Reload, Developer tools (dev builds only). Help: Check for updates.

Splicing the data block (main process, `doc-host/src/splice.js`):

```js
function splice(html, json) {
  if (typeof json !== 'string') throw new TypeError('The data must be a JSON string.');
  JSON.parse(json);                                   // reject invalid JSON
  const frame = parseDocument(html);                  // locate sections through the frame
  if (!frame.ok) throw new Error('The file does not match the document frame.');
  return buildDocument({ ...frame.parts, data: escapeJson(json) });
}
```

The data block is located through the frame parser, never by searching for its tag: the kit's own source contains the text `<script type="application/json" id="ev-data">` (it builds the frame for the browser fallback), so a text search finds a second, false data block. Because a conforming file is exactly `buildDocument(parseDocument(file).parts)`, rebuilding it changes only the data block. No regex replacement is involved, so `$` sequences in the data stay literal.

## Browser fallback

Without a host, the document saves a new copy of itself. `hours-sheet.html` pioneered this; the specification keeps the idea but replaces its DOM-clone serialisation.

| Browser | Mechanism | User experience |
| --- | --- | --- |
| Chrome, Edge | File System Access API (`showSaveFilePicker`, `createWritable`); handle stored in IndexedDB keyed by `location.href` | Pick the file once; later at most an "Allow editing" prompt per session |
| Firefox, Safari | Blob + `<a download>` | New copy lands in Downloads; the user replaces the original manually |

Serialisation without a host: **rebuild the file from the frame**, never from the live DOM. The fallback lives in the kit, so every document carries the same implementation. It reads the frame fields from the `<meta>` tags and `<html lang>`, takes the original text of the style and script sections (`textContent` of `#ev-style` and `#ev-script`, which the runtime never touches) and inserts the escaped JSON as the data section. The output always conforms, and a fallback save produces the same bytes as a host save.

Why not a DOM clone: anything the script changes at runtime (body classes, injected nodes such as datalists, a changed title) would leak into the saved file and break the frame, and DOM serialisation reformats the whole file.

Constraint this imposes: the parser normalises CRLF to LF inside sections, so documents use LF line endings only (checked on open).

Known limits: `fetch` of sibling files is blocked on `file://`; the stored handle breaks when the file moves; clearing site data forgets it.

## Security model

Every document is untrusted code: it may only render itself and save its own data block, nothing else.

Microsoft's HTA format is the cautionary precedent: HTML documents ran with full system rights and became a common malware vector. The host must never grant documents more power than a web page has.

Required settings and checks:

- `webPreferences`: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webSecurity: true`.
- **No path from the page.** The path is resolved in the main process from `event.sender.id`. The API has no path parameter.
- **No navigation.** Block `will-navigate` and `will-redirect`; deny `setWindowOpenHandler`; open no new windows.
- **Custom protocol, closed by default.** Documents are served by the main process under `ev-doc://<random-id>/` (`protocol.handle`), a fresh random id per opened document. The handler answers exactly that one URL with the file content and a CSP header (`default-src 'none'; style-src 'unsafe-inline'; script-src 'unsafe-inline'; img-src data: blob:; font-src data:`); every other request on the scheme returns 404. `file://`, `http(s)://` and all other schemes are blocked for document sessions. The document never learns its real path.
- **Network.** M1 does no name resolution at all (`host-resolver-rules` maps every name to "not found"), so documents cannot leak data through DNS lookups such as dns-prefetch. WebRTC UDP is disabled, and every document session goes through a proxy that refuses every connection. M3 adds one exception for the update feed. The only network access in the whole host is auto-update, made by the main process (not by any document session) to one fixed update feed.
- **No input to subframes.** The host injects a user style that gives iframes and frames no pointer input, so a file dropped onto one lands on the document itself, where the host opens it. A document does not receive dropped files; it can import files through a file picker or paste. Known limit of M1: the drop guard is a set of event listeners the preload adds to the page, and `document.open()` removes every listener on the page. A document that calls it after loading receives files the user drops onto it afterwards (their contents, not their paths). The isolated preload cannot stop the call reliably (a patched `document.open` can be bypassed through another frame's copy); closing this needs a guard outside the page.
- **Size limits.** Documents over 60 MB are refused on open; data blocks over 50 MB are not written. The 60 MB limit is checked only on open in M1.
- **No permissions.** `setPermissionRequestHandler` denies camera, microphone, geolocation, notifications etc.
- **Validate writes.** The host rejects `doc:save-data` with non-string input, invalid JSON and payloads over a size limit (e.g. 50 MB).
- **Data, not code (permanent).** The Host API is data-only in every version. The host writes the data block on save and the kit on a user-confirmed kit update; it never writes the style or script section on behalf of a document. Kit text comes only from the host's own list of published kits, never from the document, so a document cannot rewrite any code through the API.
- **Origin isolation.** The random id gives each opened document its own origin, so documents cannot read each other's storage.
- **No persistent browser storage.** Document sessions run in memory (no `persist:` partition): `localStorage`, IndexedDB and caches are empty on every open and leave no traces on disk. View state (filters, scroll position) lasts one session; whatever should survive belongs in the data block.

## Compatibility and versioning

The host never breaks an old document: API versions are only ever added, and documents degrade gracefully when a feature is missing.

- **API versions.** The host reads `ev-host-api` before loading. It supports every version it has ever shipped. A document asking for a newer version than the host knows is refused, like any other conformance violation: "This document needs a newer EverythingApp (API v2). Update the host, or open it in Chrome."
- **Feature detection.** Documents check `window.evHost` and `evHost.version` and keep a working browser path.
- **Data versus behaviour.** Because data lives in one block, a document's behaviour can be replaced while its content stays. The `ev-doc-type` meta tag identifies which behaviour a file carries.
- **Template upgrade (post v0.1).** The host offers "Upgrade document": regenerate the behaviour, or take a newer template, for the same `ev-doc-type`, insert the old data block, keep the previous file in the version store. If the data shape changed, the new template ships a `migrate(oldData, fromVersion)` function that runs once on load.

## Platform choice

We build the host with Electron, because it ships its own Chromium and so renders every document identically on every machine and over time.

Since the host is the product, its engine defines what every document can rely on. One known Chromium version also gives the specification and the skill a single, fixed target to generate for.

| Criterion | Electron | Tauri |
| --- | --- | --- |
| Web engine | Bundled Chromium, same everywhere | System webview: WebKit on macOS, WebView2 on Windows, WebKitGTK on Linux |
| Rendering consistency | Identical across platforms | Can differ per OS and OS version |
| Installer size | about 100 MB | about 5–10 MB |
| Backend language | JavaScript (Node.js) | Rust |
| Fit for v0.1 | Fast start, same engine as the Chrome fallback | Revisit if size or memory become a problem |

| Project | What it shows | Lesson for us |

## Open questions

- [ ] **Where generation happens.** v0.1: generation and behaviour improvement happen outside the host (e.g. Claude Code editing the file). Still open: should a later host offer "New document from description…" / "Improve this document…" and call Claude itself?
- [ ] **Skill scope.** Should the skill only generate documents, or also inspect and repair documents that fail the conformance check (the host's copyable report is its natural input)? Note: the skill should target the API version of the user's installed host, so newer-API refusals stay rare.
- [x] **File extension.** Resolved: any extension; a file is a document by content (the `ev-host-api` meta tag). `<name>.ev.html` is a recommended convention. The host is an opt-in handler for `.html` and passes non-documents to the default browser.
- [x] **Self-modifying documents.** Resolved: never. A document cannot write its own behaviour through the Host API, in any API version. Behaviour changes come only from outside the document: an agent or the skill editing the file, or the host's own kit and template updates.
- [ ] **Privileges requested by a document** *(target: M4, start of v0.2)*. A document has no privileges unless the user grants them. Design questions: where a request is declared (statically in the document, or at runtime); what a grant is bound to (path, document type, or a hash of the behaviour; an agent that rewrites the behaviour must not inherit a grant); where grants are stored and how the user revokes them (needs host UI, so after M2); how the browser fallback differs. First candidate privileges: drag-and-drop import into a document (in M1, dropped files and folders do not reach a document, except through the `document.open()` limit in the security model), network to one fixed origin, direct host-to-host connection (shared editing). Already possible without a privilege, because the user controls them: importing through a file picker (`<input type="file">`) and paste.
- [ ] **Agent connector.** A later host may expose an MCP server or connector so agents can edit an open document live through the host instead of on disk (the host would apply the edit, keep a version and reload the view, avoiding external-change conflicts). This is an agent-facing channel of the host, not part of the Host API documents see, so it does not conflict with the rule above. Scope, permissions and confirmation model to be defined.
- [ ] **Trust indicator** *(team use)*. Deferred until documents travel between people. Likely first step: show the OS origin flag (macOS quarantine, Windows Mark-of-the-Web) as a banner on first open; document signatures later.
- [x] **Concurrent edits.** Resolved: watch the file, react per section (see Host behaviour, step 6). Later: stash local data, show a diff, suggest a merge.
- [x] **Update manifest.** Resolved: GitHub Releases with `electron-updater` (electron-builder); CI builds, signs, notarises and uploads, the host reads `latest.yml` / `latest-mac.yml`. The releases must be publicly readable (public repo or a separate public releases repo). Still open: who owns the signing certificates and the release account (personal or ZHdK).
- [x] **Backups.** Resolved: central version store in the app data folder, keyed by path; no sibling files (safe in Git repos, shared and synced folders).
- [x] **Persistent per-document settings.** Resolved: none in v0.1; view state is per session, durable state lives in the data block. A host-managed `evHost.viewState` may follow in a later API version (feature-detected).

## Code session plan

Start with the host skeleton and the save loop, and write the document specification alongside it, since the specification defines what the host accepts.

Repository layout: `EverythingApp/` is the repository root for the whole system. `docs/` serves the whole system; each component (the host now, the skill later) gets its own top-level folder.

```
EverythingApp/
  docs/
    SPEC.md               # this document (currently firstSpec.md at the root)
    document-spec.md      # normative spec for documents (input for the future skill)
    reference/glossary.md
    plans/                # implementation plans per milestone
  doc-host/               # the host (Electron app)
    package.json
    src/
      main.js         # BaseWindow + WebContentsView, path map, menu, IPC
      preload.js      # window.evHost (API v1)
      protocol.js     # ev-doc:// handler, CSP, closed-by-default
      security.js     # navigation, permissions, scheme blocking
      splice.js       # data block parse + replace (pure, unit-tested)
      conformance.js  # frame, sections, kit hash, line endings, API version
      write.js        # version store, temp file, rename
      watch.js        # external-change detection, section hashes
    kit/
      ev-kit-1.0.0.js # published kit texts; hashes generated at build time
    fixtures/
      hours-sheet.ev.html  # first conforming document
      invalid/             # broken documents for conformance tests
    test/
      splice.test.js
      conformance.test.js
      kit.test.js          # fallback rebuild == host save, byte for byte
  hours-sheet.html        # the original prototype, kept until task 10
```

M1 tasks, in order:

1. Scaffold the Electron app on `BaseWindow` + `WebContentsView`; open a document via dialog, command-line argument and drag-and-drop.
2. Write `docs/document-spec.md` v1 from the "Document specification" and "Host API v1" sections, including the frame and the `ev` namespace.
3. Write kit 1.0.0 (data loading, host wiring, fallback rebuild from the frame) and `kit.test.js`.
4. Implement `splice.js` with tests: single data block, `<` escaping, `$` in data, invalid JSON, missing or duplicate data block.
5. Implement `conformance.js` with tests against `fixtures/invalid/`; run it on open; refusal dialog with "Copy report" and the Chrome hint.
6. Implement `protocol.js` and `security.js`; verify that a document cannot navigate, open windows, reach the network or read `file://`.
7. Implement `preload.js`, the `doc:save-data` handler with change counter, and `write.js` (version store, temp file, rename).
8. Add the menu (Ctrl/Cmd+S → `doc:request-save`), dirty marker in the title and the close prompt.
9. Implement `watch.js`: section hashes, auto-reload on behaviour change, conflict prompt on data change.
10. Adapt `hours-sheet.html` to the specification (frame, sections, kit, `ev` names, no own Save button under the host) and use it as the first fixture.
11. Walk through the acceptance criteria in the user story.

M2 and M3 are planned once M1 passes its acceptance criteria.
